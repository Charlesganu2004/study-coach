# Controlled retrieval comparison

This experiment uses the selected Groq `openai/gpt-oss-120b` model and the exact `grounded` prompt from the separate full context experiment. The changed variable is source selection: full context sends all 12 sources, while lexical retrieval sends up to four matching sources. There is one run of the same 50 cases, with the original notes, rubric, temperature of 0.2, top p of 1, allocation of 2,048 tokens, timeout, retries, and request pacing held fixed.

The retriever splits the question, source titles, and source text into distinct lowercase ASCII alphanumeric terms and removes a fixed stop word list. A question term earns three points for a title match and one for a body match. Positive scores are ranked, ties use original source order, and the first four sources are retained. Selected sources are returned in original corpus order with unchanged IDs, titles, and text. If nothing matches, the complete corpus is used. There are no embeddings, learned relevance weights, external search, or reference answer inputs.

The evaluator calls the same `core::answer` function as the application. The original complete notes are used for scoring so a missing retrieved source cannot quietly change the answer criteria. Expected citation IDs are inspected only after source selection, to diagnose retrieval coverage. The offline check found that all expected source IDs were retained in all 36 answer cases; this is development set coverage, not a measure of general retrieval relevance or answer quality.

The manifest retains exact prompt text and consistency fingerprints of the dataset, notes, scorer, retriever, source code, and configuration. These FNV1a identifiers detect accidental changes for resuming; they are not cryptographic signatures. The ledger retains the chosen source IDs, complete model response, score, usage, API errors, and timing for each call. It flushes after every outcome. Rerunning the same command resumes completed cases and retries earlier API errors without deleting them.

`latency_ms` measures the shared core call, including retry waits and excluding request pacing. `retrieval_ms` measures local source selection. `end_to_end_latency_ms` is the sum of these two measurements, excluding request pacing and file persistence. Means include completed calls; an earlier failed transport duration is not captured. Input and output token usage are recorded only when supplied by the provider.

This arm may overlap the other controlled experiment in time. Both retain their configured pacing, but provider queueing and shared quota can affect latency. The comparison should therefore report observed timing without claiming a randomized latency trial. The inference is the same model with the same prompt; source selection is the intended quality variable.

No final score is claimed before all 50 cases finish without outstanding API errors. Free cost means zero API charge only while the user's account quota covers these calls. Account billing is not independently verified and no paid fallback is enabled. One run does not establish statistical significance or model output variability. The examples are a visible development set with known phrase matching and task completion limitations.
